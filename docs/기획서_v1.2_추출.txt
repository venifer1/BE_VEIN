0. 문서 정보
1. 프로젝트 개요
1.1 한 줄 정의
베인(VEIN)은 암호화폐, 미국주식, 국내주식 시장 데이터를 통합 수집하여 기술적 패턴 탐지, 조건검색, 실시간 스캐닝, 뉴스 분석을 통해 매매 후보를 자동 발굴하는 모바일 중심 트레이딩 인텔리전스 플랫폼이다.
1.2 제품 비전
사용자가 직접 종목을 찾는 시간을 줄이고, 시스템이 먼저 매매 후보를 제안한다.
단순 차트/시세 조회가 아니라 패턴·조건·뉴스·미시지표를 결합한 실행형 신호를 제공한다.
개인투자자가 모바일에서 기관형 터미널의 핵심 의사결정 흐름을 가볍게 사용할 수 있게 한다.
1.3 핵심 전략
초기에는 모든 자산을 깊게 다루기보다, 코인/주식의 빠른 탐색과 알림 중심으로 검증한다.
무료 사용자는 시세·차트·기본 검색으로 유입시키고, PRO는 고급 조건검색·패턴 탐지·실시간 알림으로 전환한다.
1인 개발 기준으로 Next.js 모바일 웹/PWA/웹뷰 앱을 우선 출시하고, Flutter는 검증 후 전환한다.
Spring Boot 단일 서버로 시작하되 Scanner/Notification/Backtest 모듈은 분리 가능한 구조로 설계한다.

6.3 실행 방식
Batch Scanner: 1분/5분/일봉 기준으로 대상 종목을 주기 스캔
On-demand Scanner: 사용자가 직접 검색 실행 시 즉시 계산
Result Cache: 동일 조건식은 짧은 시간 Redis 캐싱
Alert Evaluator: 저장된 조건식 중 알림 활성화된 것만 별도 평가
초기 제한: 전체 종목이 아닌 주요 시장/거래대금 상위/관심종목 중심
7. Pattern Engine 설계
7.1 개요
Pattern Engine은 캔들 데이터에서 국소 고점/저점을 탐지한 뒤, 규칙 기반으로 가격 구조를 판별하여 매매 후보를 추출하는 베인의 핵심 차별화 엔진이다.
7.2 공통 탐지 프로세스
캔들 데이터 수집
국소 고점(Local High) 탐지
국소 저점(Local Low) 탐지
패턴 후보 생성
규칙 검증
Pattern Score 계산
사용자 화면에 후보 노출
7.3 ABC 검색기
목적: 조정 파동 구조를 자동 탐지해 C 예상가 근처 종목 선별
검사 항목: 0→A 하락폭, A→B 반등 비율, B→C 진행 여부, 0 돌파 여부, A 이탈 여부
결과 상태: 진행중, 완료 임박, 실패 패턴
7.4 고점판독기
ABC 알고리즘을 가격 축 반전 방식으로 재사용
상승 추세의 고점 후보, 상승 피로도, 분배 가능성을 탐지
거래량 감소, 고점 갱신 실패, 되돌림 비율을 함께 평가
7.5 삼각수렴 검색기
최근 고점 3개와 저점 3개의 수렴 구조 분석
추세선 기울기와 수렴 폭 감소율 계산
대칭/상승/하락 삼각형으로 분류
7.6 이말올 검색기
단기 반등 가능성이 높은 종목 탐지
2개 연속 양봉, 볼린저 하단 접촉, 거래량 증가, 이동평균선 회복, RSI 반등 조건 적용
8. Scanner Engine 설계
8.1 틱띄기 스캐너
틱띄기 스캐너는 실시간 체결과 호가 데이터를 기반으로 스캘핑 적합 종목을 점수화해 랭킹으로 제공한다.
8.2 Scalping Score 기본식
Scalping Score = TPS Score + Spread Score + Orderbook Score + Volatility Score + Trade Strength Score
초기에는 각 항목 20점 만점, 총 100점 기준으로 설계하고 운영 데이터에 따라 가중치를 조정한다.
9. Pattern Score Engine
9.1 목적
여러 패턴 후보 중 어떤 종목을 상위에 노출할지 결정하기 위해 정량 점수 체계를 둔다. 점수는 후보의 완성도, 거래량, 추세, 변동성, 뉴스 모멘텀을 종합한다.
9.2 기본 점수 체계
9.3 표시 예시

- 거래량 +320%

10. Explain Engine
10.1 목적
사용자가 결과를 신뢰할 수 있도록 “왜 이 종목이 잡혔는지”를 짧고 명확하게 설명한다. 점수만 보여주는 것이 아니라 조건 충족 근거를 함께 보여준다.
10.2 설명 구성

점수 세부 항목
주의 요인
다음 확인 포인트
10.3 예시
SOL이 삼각수렴 후보로 탐지되었습니다.
- 최근 고점 3개는 낮아지고 저점 3개는 높아지는 대칭 수렴 구조입니다.
- 거래량은 평균 대비 180% 증가했습니다.
- 현재가는 상단 추세선까지 1.2% 남아 있습니다.

20. 보안/권한/법적 고지
20.1 보안 요구사항

20.2 금융/법적 고지
본 서비스는 투자 참고용 정보 제공 서비스이며 투자 권유가 아님을 명시
투자 판단과 책임은 사용자 본인에게 있음을 명시
시세 데이터 지연 여부와 출처를 화면에 표시

25.2 재사용 원칙
재사용 대상은 UI 코드가 아니라 탐지 규칙, 계산식, 외부 API 계약, 예외 처리 경험, 테스트 데이터다.
Python 탐지 결과를 골든 데이터셋으로 고정하고 Java 엔진이 동일 입력에서 허용 오차 내 동일 결과를 내는지 회귀 테스트한다.
데스크톱 MySQL 스키마를 신규 PostgreSQL 운영 스키마로 그대로 복제하지 않는다. 도메인 모델을 새로 정의하고 필요한 데이터만 마이그레이션한다.
신규 서비스와 레거시 앱의 동시 쓰기(dual write)는 금지한다. 전환 기간에는 레거시를 읽기 전용 검증 도구로 사용한다.

26.2 MVP 성공 기준
가입 사용자가 관심종목을 등록하고 3분 이내에 조건 또는 패턴 알림 1개를 만들 수 있다.
알림 생성 사용자 중 7일 내 재방문율, 패턴 결과 클릭률, 알림 클릭률을 핵심 검증 지표로 본다.
유료 전환 전 최소 2주간 탐지 정확도, 중복 알림률, 데이터 누락률을 운영 데이터로 측정한다.
27. 엔진 이관과 시스템 설계 보강
27.1 데이터 계약
모든 공급사는 MarketDataProvider 인터페이스 뒤에 격리한다. 공급사 응답 DTO와 내부 Quote/Candle 모델을 분리한다.
종목 식별자는 내부 instrument_id를 기준으로 하고 UPBIT:KRW-BTC, BINANCE:BTCUSDT처럼 공급사 심볼을 별도 매핑한다.
캔들은 UTC 시작 시각, 시장, 타임프레임, OHLCV, 공급사, 수집 시각을 필수 필드로 둔다.
외부 API 실패 시 타임아웃, 재시도, 지수 백오프, 서킷 브레이커, 최근 정상값 유지 정책을 공급사별로 정의한다.
27.2 Pattern Engine 이관
1단계: Python 엔진에서 대표 성공·실패·경계 사례를 JSON fixture로 추출한다.
2단계: ABC와 삼각수렴부터 순수 Java 라이브러리로 포팅하고 DB·네트워크 의존성을 제거한다.
3단계: 골든 테스트, 파라미터 경계 테스트, 미래 데이터 참조 방지 테스트를 통과한 뒤 Scanner에 연결한다.
4단계: 이말올, 고점판독, 틱띄기 점수 순으로 이관한다.
Pattern Score와 Explain은 탐지 엔진과 분리한다. 탐지 결과가 먼저 사실을 만들고, 점수와 설명은 그 결과를 소비한다.
27.3 운영 경계
Spring Boot API 서버는 요청 처리와 사용자 도메인을 담당하고, 주기 스캔은 동일 코드베이스의 별도 worker 프로세스로 실행한다.
Redis는 결과 캐시, 분산 락, 알림 중복 방지에 사용한다. 영속 원본은 PostgreSQL로 단일화한다.
웹소켓은 시세 스트림과 스캐너 결과 갱신에만 사용하고, 알림 전달 보장은 notifications 테이블과 발송 상태로 관리한다.
28. 비기능 요구사항과 완료 기준
API: 일반 조회 p95 500ms 이하, 캐시 적중 시 p95 200ms 이하를 목표로 한다.
스캐너: 5분봉 기준 대상 코인 전체 평가를 다음 주기 시작 전 완료하고, 지연 시 중복 실행을 막는다.
알림: 동일 사용자·규칙·종목·신호는 cooldown 내 1회만 생성하며 모든 발송 시도와 실패 사유를 기록한다.
정확성: 캔들 확정 전후를 구분하고, 백테스트와 탐지에서 미래 봉을 참조하지 않는다.
보안: 비밀키는 저장소에 커밋하지 않고 환경 변수 또는 Secret Manager로 주입한다.
관측성: 외부 API 오류율, 스캔 소요시간, 탐지 건수, 알림 성공률, 큐 적체를 메트릭으로 수집한다.
테스트: 도메인 단위 테스트, 공급사 계약 테스트, 엔진 골든 테스트, 핵심 사용자 흐름 E2E 테스트를 CI에서 실행한다.
법적: 자동 주문 기능은 MVP에서 제공하지 않으며 모든 신호 화면에 투자 참고용 고지를 노출한다.

30. Signal Lifecycle Engine
30.1 목적
패턴이나 조건이 한 번 탐지된 사실만 저장하지 않고, 생성부터 확인·무효화·만료까지 상태 변화를 추적한다. 이를 통해 중복 노출을 줄이고 실제 성과를 객관적으로 측정한다.
30.2 상태 정의
미확정 봉에서 생성된 신호는 provisional=true로 저장하며 확정 신호와 시각적으로 구분한다.
상태 전환은 signal_events에 이력으로 남기고 현재 상태만 덮어쓰지 않는다.
중복 키는 engine_version, rule_id, instrument_id, timeframe, anchor_candle_time 조합을 기본으로 한다.
사용자 화면에는 신호 생성 시각, 기준 봉, 현재 상태, 만료 예정 시각을 표시한다.
31. Signal Performance & Learning Loop
31.1 실제 성과 추적
탐지 가격과 1시간, 4시간, 1일, 3일, 7일 후 가격·수익률을 자동 저장한다.
신호 이후 최대 유리 변동(MFE), 최대 불리 변동(MAE), 목표가·손절가 최초 도달 시각을 계산한다.
코인 24시간 시장과 주식 거래시간을 구분해 평가 시점을 계산한다.
성과는 패턴, 시장, timeframe, 엔진 버전, 점수 구간별로 집계한다.
성과 데이터는 매매 수익 인증이 아니라 탐지 품질 측정용임을 명시한다.
31.2 평가 지표
31.3 개선 루프
탐지 → 상태 추적 → 성과 평가 → 버전별 리포트 → 파라미터 후보 제안 → 검증 후 배포 순으로 운영한다.
운영 성과가 나쁘다는 이유만으로 자동으로 파라미터를 변경하지 않는다. 변경안은 백테스트와 별도 검증을 통과해야 한다.
엔진 변경 전후 성과는 동일 시장·기간·종목군으로 비교해 데이터 편향을 줄인다.
32. Unified Signal Inbox & Alert Simulator
32.1 통합 신호함
ABC, 삼각수렴, 조건검색, 이말올, 틱띄기 결과를 하나의 신호 모델과 화면으로 통합한다.
같은 종목에서 여러 신호가 발생하면 종목 카드에 묶되 신호별 근거와 상태는 유지한다.
사용자 상태는 NEW, SEEN, WATCHING, DISMISSED로 관리하고 엔진 상태와 분리한다.
필터는 시장, 패턴, timeframe, 점수, 상태, 발생 시각, 관심종목 여부를 지원한다.
후보 3개까지 점수, 진행률, 거래량, 유동성, MFE·MAE 통계를 비교하는 기능을 제공한다.
32.2 알림 사전 시뮬레이션
알림 저장 전 최근 7일 또는 30일 데이터로 예상 발생 횟수와 대상 종목 수를 보여준다.
예상 빈도가 높은 규칙은 조건 강화, cooldown 확대, 관심종목 한정 옵션을 제안한다.
시뮬레이션은 확정 봉 기준의 근사치이며 실제 발생 횟수와 다를 수 있음을 표시한다.
무료 플랜의 알림 제한은 생성 규칙 수뿐 아니라 월 평가량과 발송량을 함께 고려한다.
33. Data Quality & Risk Guard
33.1 데이터 신뢰도
모든 시세와 신호에 공급사, 수집 시각, 마지막 정상 갱신 시각, 지연 시간, 확정 봉 여부를 연결한다.
캔들 누락, 시간 역전, 비정상 OHLC, 중복 봉, 장시간 미갱신을 자동 검증한다.
품질 상태는 HEALTHY, DELAYED, PARTIAL, INVALID로 분류한다.
INVALID 데이터에서는 신규 신호와 알림 생성을 차단하고, PARTIAL은 화면 경고 후 정책에 따라 제한한다.
공급사 장애 및 데이터 보정 후 어떤 신호가 영향을 받았는지 추적할 수 있어야 한다.
33.2 거래 가능성 리스크 필터
최소 거래대금, 최대 스프레드, 최소 상장 기간, 최소 캔들 수를 시장별 기본 필터로 둔다.
급격한 갭, 거래정지, 상장폐지 예정, 과도한 단기 변동성, 호가 부족 종목은 경고 또는 제외한다.
Risk Guard 결과는 PASS, WARN, BLOCK으로 반환하고 차단 이유를 Explain에 포함한다.
사용자는 경고 기준을 완화할 수 있지만 시스템 기본 차단 사유와 데이터 오류는 우회할 수 없다.

36. Paper Trading Engine
36.1 목적과 범위
실시간 신호를 가상 주문과 포지션으로 연결해 백테스트와 실제 시장 사이의 실행 가능성을 검증한다. Paper Trading은 교육·검증 기능이며 거래소 주문 API와 사용자 자금을 사용하지 않는다.
지원 주문은 시장가, 지정가, 손절, 목표가로 시작하며 복합 주문은 후순위로 둔다.
사용자는 초기 가상자산, 포지션 크기 방식, 최대 동시 포지션, 기본 손절·목표 수익률을 설정한다.
신호 상세에서 가상 진입하거나 규칙별 자동 Paper Trading을 활성화할 수 있다.
자동 가상 진입은 사용자별 한도, Risk Guard, 데이터 품질 PASS 조건을 모두 충족해야 한다.
현금, 주문, 체결, 포지션, 실현·미실현 손익을 원장 방식으로 기록하고 과거 값을 덮어쓰지 않는다.
36.2 주문 상태
36.3 Paper Trading 성과
총수익률, 실현손익, 승률, Profit Factor, MDD, 평균 보유기간, 회전율을 제공한다.
신호 이론 수익률과 가상 체결 순수익률의 차이를 execution gap으로 표시한다.
성과 화면은 세금 효과를 기본적으로 포함하지 않으며 포함 범위를 명시한다.
계정 초기화 시 기존 기록은 삭제하지 않고 새 simulation_run으로 분리한다.
37. Execution Realism Engine
37.1 현실 체결 모델
모든 성과 계산에 시장별 매수·매도 수수료를 반영하고 적용된 요율 버전을 저장한다.
시장가는 당시 최우선 호가와 주문 수량 대비 호가 깊이를 이용해 VWAP 방식으로 가상 체결한다.
호가 이력이 없으면 거래대금·스프레드·변동성 기반 보수적 슬리피지 모델을 사용하고 estimated=true로 표시한다.
지정가는 가격 도달만으로 체결하지 않고 거래량 참여율과 대기 순서 가정을 반영한다.
부분 체결, 미체결, 주문 지연, 급격한 갭을 지원하며 미래 데이터로 체결 여부를 소급 결정하지 않는다.
동일 체결 모델을 Paper Trading과 Backtest가 공유해 계산 불일치를 방지한다.
37.2 기본 체결 파라미터
38. Portfolio Risk Engine
38.1 위험 측정
포트폴리오 총 평가액, 현금 비중, 종목·시장·섹터별 노출과 미실현 손익을 계산한다.
동일 기초자산과 높은 상관관계를 가진 종목을 묶어 집중 위험을 표시한다.
단일 종목 최대 비중, 시장 최대 비중, 일일 손실 한도, 최대 동시 포지션을 설정한다.
변동성 기반 포지션 크기와 포트폴리오 열(portfolio heat)을 계산한다.
초기에는 Historical VaR과 스트레스 시나리오를 참고 지표로만 제공하고 손실 보장 지표로 표현하지 않는다.
38.2 주문 전 검증
BLOCK은 자동 Paper Trading 주문을 거절하고 수동 주문에는 차단 이유를 명확히 표시한다.
실거래가 아니더라도 사용자의 위험 설정 변경과 우회 이력을 감사 로그에 남긴다.
39. Market Regime Engine
39.1 국면 분류
시장 국면은 BULL_TREND, BEAR_TREND, RANGE, HIGH_VOLATILITY, TRANSITION으로 시작한다.
장기·중기 이동평균 기울기, ADX, 실현 변동성, 시장 폭, 거래량을 규칙 기반으로 결합한다.
분류는 시장과 timeframe별로 수행하며 regime_version과 입력 스냅샷을 저장한다.
확정되지 않은 국면은 TRANSITION 또는 confidence가 낮은 상태로 표시하고 강제 분류하지 않는다.
39.2 신호 연계
신호 성과를 패턴·시장·timeframe·국면 조합으로 분리 집계한다.
Pattern Score에는 국면 적합도를 별도 항목으로 표시하되 원본 탐지 결과를 변경하지 않는다.
표본이 부족한 국면에서는 점수 가중치를 적용하지 않고 참고 정보만 제공한다.
국면 전환 시 기존 포지션에 위험 재평가 이벤트를 생성한다.
40. Signal Confidence & Evidence
40.1 신뢰도 구성
Pattern Score는 현재 후보의 구조적 적합도이고 Confidence는 과거 근거의 충분성과 안정성이다. 두 값을 하나의 숫자로 합치지 않는다.
사용자에게 점수, 신뢰도 등급, 평가 표본 수, 평가 기간, 국면을 함께 표시한다.
초기 등급은 INSUFFICIENT, LOW, MEDIUM, HIGH로 구분한다.
최소 표본 미달 시 높은 Pattern Score라도 신뢰도 부족 경고를 표시한다.
여러 조건을 반복 탐색해 우연히 좋은 결과만 선택하는 다중검정 편향을 운영 검토 항목에 포함한다.
40.2 성과 공개 원칙
성과에는 수수료·슬리피지 포함 여부, 표본 수, 기간, 생존자 편향 가능성을 표시한다.
상장폐지·거래정지·심볼 변경 종목을 가능한 범위에서 평가 모집단에 포함한다.
과거 성과가 미래 수익을 보장하지 않으며 Paper Trading은 실제 체결과 다를 수 있음을 고지한다.
41. Operational Control & Cost Governance
41.1 배포와 장애 대응
엔진, 알림, Paper Trading, AI 기능은 Feature Flag로 독립 활성화하고 긴급 Kill Switch를 둔다.
엔진 새 버전은 Shadow 실행, 일부 트래픽 Canary, 전체 배포 순으로 진행한다.
이전 버전과 신호 수·성과·오류율 차이가 임계값을 넘으면 자동 중단 또는 수동 롤백한다.
주 공급사 장애 시 대체 Provider로 전환하되 가격 차이와 데이터 연속성을 검증한다.
알림은 CREATED, QUEUED, SENT, DELIVERED, CLICKED, FAILED 상태로 추적한다.
초기 운영 목표는 데이터·스캐너·알림별 SLO와 RTO/RPO를 구분해 정의한다.
41.2 과금과 원가
사용자별 스캔 평가량, 알림 발송량, AI 토큰, 데이터 API 호출량을 usage_events로 기록한다.
무료·PRO·PRO+는 기능 잠금뿐 아니라 일·월 사용량, 보관 기간, 리포트 범위로 구분한다.
결제 실패, 유예 기간, 다운그레이드, 환불, 구독 만료 후 데이터 접근 정책을 정의한다.
데이터 공급사별 재배포 권한과 예상 월 원가를 출시 게이트로 관리한다.
사용자는 개인정보·전략·Paper Trading 기록을 내보내고 탈퇴 시 정책에 따라 삭제 요청할 수 있다.

43.1 과적합 방지 원칙

시장 시계열 특성을 고려해 임의 셔플 대신 Walk-forward 검증을 기본으로 한다.

백테스트, Paper Trading, 운영 성과를 분리 표시하고 하나의 성과 수치로 합치지 않는다.
운영 중 규칙 변경은 새 rule_version으로 배포하며 과거 결과를 새 버전 성과로 소급 편입하지 않는다.

44. Data Lineage & Correction
44.1 데이터 계보
원시 응답, 정규화 레코드, 캔들 revision, 지표 스냅샷, 신호, 설명, 성과 간 lineage_id를 연결한다.
외부 공급사 응답은 수집 시각, 요청 키, 응답 해시, 스키마 버전, 파서 버전을 기록한다.
신호 상세에서 데이터 출처와 계산 버전을 감사 가능한 수준으로 추적할 수 있어야 한다.
민감 정보와 대용량 원본은 별도 보관 정책을 적용하고 무기한 저장하지 않는다.
44.2 정정과 재처리
공급사 정정 또는 결측 복구 시 새 data_revision을 생성하고 기존 원본을 조용히 덮어쓰지 않는다.
영향 분석 작업은 수정된 캔들에서 파생된 지표, 신호, 알림, Paper 체결, 성과 목록을 산출한다.
재계산 결과가 달라지면 before·after와 변경 사유를 correction_events에 기록한다.
이미 발송된 알림은 삭제하지 않고 정정 배지와 필요 시 후속 안내를 제공한다.
재처리는 idempotent해야 하며 동일 revision을 반복 적용해도 중복 결과가 생기지 않아야 한다.
45. Ledger Integrity & Reconciliation
45.1 원장 불변식
가상 현금 변화는 입출금, 수수료, 체결, 실현손익 원장 항목의 합으로만 계산한다.
주문 체결 수량 합은 주문 수량을 초과할 수 없고 포지션 수량은 체결 원장으로 재구성 가능해야 한다.
모든 쓰기 요청은 idempotency_key를 지원해 재시도 시 중복 주문과 중복 체결을 막는다.
주문·체결·포지션 변경은 하나의 트랜잭션 또는 복구 가능한 이벤트 흐름으로 처리한다.
금액과 수량은 부동소수점 대신 시장별 정밀도를 가진 Decimal로 저장한다.
45.2 대사와 복구
대사 실패는 조용히 보정하지 않고 incident와 audit log를 생성한다.
장애 복구 테스트는 중간 실패, 중복 메시지, 순서 역전, DB 재시작 시나리오를 포함한다.
46. Security, Privacy & Abuse Prevention
46.1 위협 모델과 인증
계정 탈취, 토큰 탈취, 권한 상승, 관리자 오용, 데이터 유출, 리소스 고갈을 핵심 위협으로 정의한다.
관리자와 중요 기능 사용자는 TOTP 또는 WebAuthn 기반 2FA를 적용한다.
비밀번호·2FA·이메일·구독·위험 한도 변경에는 최근 인증 또는 재인증을 요구한다.
사용자는 활성 세션과 기기를 조회하고 개별 또는 전체 로그아웃할 수 있다.
Refresh Token은 회전·재사용 탐지·폐기 정책을 적용하고 원문을 저장하지 않는다.
PII와 비밀값은 저장·전송 시 암호화하며 관리자 조회도 목적과 사유를 감사 로그에 남긴다.
46.2 권한과 관리자 통제
RBAC에 리소스 범위와 환경을 결합하고 운영·스테이징 권한을 분리한다.
Feature Flag 전체 중단, 데이터 재처리, 사용자 가장, 대량 내보내기는 이중 승인 대상으로 둔다.
관리자 화면에서 비밀번호, 토큰, 전체 개인정보를 직접 노출하지 않는다.
권한 변경, 로그인 실패 급증, 비정상 대량 조회는 보안 이벤트로 탐지한다.
46.3 남용 방지
로그인, 회원가입, 종목 검색, 스캔, 알림, 백테스트, AI 요청별 Rate Limit과 비용 한도를 둔다.
IP, 계정, 기기, 결제 수단 신호를 조합해 무료 계정 반복 생성과 자동화 남용을 탐지한다.
비싼 작업은 동시 실행 수, 큐 우선순위, 일일 quota로 통제한다.
차단은 ALLOW, CHALLENGE, THROTTLE, BLOCK 단계로 적용하고 오탐 이의 처리 절차를 둔다.
47. Experimentation & Model Change Control
A/B 실험은 가설, 대상, 기간, 1차 지표, 보호 지표, 중단 기준을 시작 전에 등록한다.
사용자 배정은 안정적인 experiment_key로 유지하며 동일 사용자가 집단을 반복 이동하지 않게 한다.
Pattern Score 실험은 클릭률뿐 아니라 신호 성과, 알림 해제율, 위험 경고 무시율을 함께 본다.
여러 실험의 동시 노출 충돌을 관리하고 결제·보안·법적 고지에는 무작위 실험을 제한한다.
보호 지표가 임계값을 넘으면 실험을 자동 중단하고 원인을 기록한다.
실험 종료 후 결과와 의사결정을 남기고 유리한 결과만 선택적으로 보고하지 않는다.
48. Notification Quality & User Control
48.1 전달 품질
신호 발생, 알림 생성, 큐 진입, 공급사 발송, 단말 수신, 클릭 시각을 분리 측정한다.
중요도는 CRITICAL, HIGH, NORMAL, DIGEST로 구분하되 투자 신호를 안전 경보처럼 과장하지 않는다.
동일 종목·유사 신호는 설정된 시간창에서 묶고 중복·지연·순서 역전을 탐지한다.
오래 지연되어 의미가 없어진 알림은 발송하지 않고 EXPIRED 처리한다.
알림 클릭은 정확한 signal_id와 당시 상태 화면으로 이동하며 삭제된 신호도 감사 화면을 제공한다.
48.2 사용자 제어
사용자 지역 시간 기준 Quiet Hours와 시장별 예외를 지원한다.
즉시, 시간별 요약, 일일 요약 중 전달 방식을 선택할 수 있다.
장기간 열지 않는 유형은 빈도 축소를 제안하되 사용자 동의 없이 중요 알림을 끄지 않는다.
알림 설정 변경 전 예상 발생 빈도와 최근 전달 성공률을 표시한다.
49. Reliability, Backup & Incident Response
49.1 SLO와 장애 등급
SEV1은 광범위 데이터 오류, 원장 불일치, 보안 침해 가능성으로 정의하고 즉시 기능 중단을 허용한다.
SEV2는 핵심 기능 장애, SEV3는 제한적 품질 저하로 분류한다.
49.2 백업과 복구
PostgreSQL은 자동 백업과 Point-in-Time Recovery를 구성하고 백업 암호화·보존 기간을 정의한다.
Redis는 원본 저장소로 사용하지 않으며 유실 시 PostgreSQL과 이벤트로 재구성 가능해야 한다.
복구 훈련은 분기 1회 이상 수행하고 실제 RTO·RPO와 실패 항목을 기록한다.
공급사 장애, 캔들 오염, 알림 폭주, 중복 체결, DB 장애, 키 유출 Runbook을 작성한다.
장애 종료 후 타임라인, 영향, 근본 원인, 재발 방지 조치를 Postmortem으로 남긴다.
50. Mobile Product Readiness
온보딩은 관심시장 선택, 관심종목 등록, 첫 알림 생성, 알림 권한 요청 순서로 구성한다.
알림 권한은 앱 첫 실행 즉시 요구하지 않고 사용자가 가치와 예시를 확인한 뒤 요청한다.
로딩, 빈 데이터, 지연 데이터, 부분 실패, 오프라인, 권한 거부 상태를 화면별로 설계한다.
저속 네트워크에서는 마지막 정상 데이터와 갱신 시각을 표시하고 요청 취소·재시도를 지원한다.
WCAG 2.2 AA 수준의 색상 대비, 글자 확대, 키보드 탐색, 스크린리더 레이블을 목표로 한다.
저사양 Android와 모바일 Safari를 포함한 지원 기기 기준과 성능 예산을 정의한다.
딥링크는 인증 전후 목적지를 보존하고 권한이 없는 화면은 안전한 대체 화면으로 이동한다.

52. Canonical Event & Data Contract
시세, 캔들, 신호, 주문, 체결, 알림은 공통 event_id, event_type, schema_version, occurred_at, produced_at, trace_id를 가진다.
이벤트 스키마는 하위 호환을 원칙으로 하고 필드 삭제·의미 변경은 새 major schema_version으로 배포한다.
Producer와 Consumer 간 Contract Test를 CI에서 실행하고 미등록 스키마 이벤트를 운영 큐에 발행하지 않는다.

53. Queue, Backpressure & Workload Isolation
큐 깊이, oldest message age, 처리율, 실패율을 메트릭으로 수집하고 단계별 부하 차단 기준을 둔다.
Dead Letter Queue는 원인·재시도 횟수·원본 참조를 보존하고 무한 재시도를 금지한다.
무거운 백테스트가 시세 수집과 알림 전송 자원을 잠식하지 않도록 worker pool과 DB 연결 한도를 분리한다.
54. Capacity Planning & Performance Budget
등록 종목 수, timeframe 수, 초당 시세 이벤트, 동시 사용자, 알림 fan-out을 기준으로 월별 용량 모델을 작성한다.
API, WebSocket, Scanner, DB, Redis, Queue별 부하 테스트 시나리오와 한계점을 기록한다.
모바일 초기 화면은 핵심 콘텐츠 LCP 2.5초, 상호작용 INP 200ms를 목표로 성능 예산을 관리한다.
성능 개선은 캐시 적중률만 보지 않고 데이터 최신성과 오류 은폐 여부를 함께 검증한다.
55. Storage Lifecycle & Query Architecture
최근 캔들·신호는 hot storage, 오래된 원본·성과는 partitioned warm storage, 감사·백업은 archive 계층으로 분리한다.
대용량 시계열 테이블은 market·time 기준 파티셔닝과 보존 정책을 적용한다.
운영 트랜잭션 조회와 분석 집계를 분리하고 무거운 리포트가 주문·알림 DB를 방해하지 않게 한다.
삭제 요청과 법적 보존이 충돌할 경우 데이터 분류표와 승인 절차를 따른다.
56. Provider Portability & Data Economics
공급사별 기능, 정확도, 지연, 호출 제한, 재배포 권리, 월 비용을 provider scorecard로 관리한다.
동일 내부 모델로 두 공급사를 Shadow 비교해 가격 편차와 결측률을 측정한 뒤 전환한다.
공급사 종속 식별자와 오류 코드를 도메인 모델에 노출하지 않는다.
대체 공급사가 없는 기능은 화면과 로드맵에 single-provider risk로 표시한다.
57. FinOps & Unit Economics
예산 임계값은 알림만 보내지 않고 비핵심 배치 축소, AI 제한, 리포트 지연 같은 단계별 대응과 연결한다.
비용 절감을 위해 데이터 품질이나 법적 라이선스 범위를 희생하지 않는다.

60. Requirements Traceability
모든 요구사항은 화면, API, 데이터 모델, 테스트 케이스, 운영 메트릭에 연결되는 고유 ID를 가진다.
구현 완료는 코드 병합이 아니라 acceptance criteria와 관측성·문서화까지 충족한 상태다.
61. API & Schema Compatibility Contract
Public API는 /api/v1을 사용하고 breaking change는 병행 운영 기간과 마이그레이션 가이드 없이 배포하지 않는다.
오류 응답은 code, message, trace_id, field_errors를 포함하며 내부 예외와 공급사 원문을 노출하지 않는다.
목록 API는 cursor pagination, 안정적 정렬 키, 최대 page size를 표준화한다.
시간, 가격, 수량, 통화, percentage의 단위와 Decimal 직렬화 규칙을 API 계약에 고정한다.
OpenAPI diff와 DB migration 검사를 CI 출시 차단 조건으로 사용한다.
62. Test Pyramid & Release Evidence
Flaky test는 재실행으로 숨기지 않고 소유자와 수정 기한을 부여한다.
운영 데이터 복사본은 개인정보 제거와 접근 승인을 거친 테스트 fixture로만 사용한다.
63. Migration & Rollback Contract
DB 변경은 Expand-Migrate-Contract 순서로 배포하고 구버전 애플리케이션과의 짧은 공존을 허용한다.
대용량 backfill은 배치 크기, 중단·재개, 진행률, 검증 쿼리, 롤백 계획을 가진다.
애플리케이션 롤백과 데이터 롤백을 구분하고 파괴적 migration은 백업·복원 검증 전 실행하지 않는다.
Feature Flag가 DB 스키마 불일치를 해결해 주는 것으로 간주하지 않는다.
64. Launch Operations Contract
출시 2주 전 코드 동결 기간, 담당자, 모니터링 대시보드, 고객 공지, 지원 대응 문구를 확정한다.
출시 당일에는 트래픽, 가입, 데이터 지연, 스캔 지연, 알림 실패, 원장 대사, 비용을 실시간 확인한다.
Go/No-Go 결정자는 제품, 개발, 운영, 보안 관점의 체크 결과를 기록한다.
출시 후 24시간·72시간·7일 리뷰에서 문제와 롤백 여부를 재평가한다.
65. v1.0 Definition of Done
66. Customer Support Operating Model
문의 유형을 계정·결제·데이터·신호·알림·Paper Trading·보안·개인정보로 분류하고 담당 큐와 응답 목표를 둔다.
고객지원 도구는 최소 권한으로 구성하며 사용자 가장 기능은 명시적 승인과 감사 로그를 요구한다.
지원 답변은 투자 판단을 대신하거나 수익을 약속하지 않고 데이터·기능 동작을 설명한다.
반복 문의는 제품 결함·문서 부족·오해 유발 UX로 분류해 개선 backlog에 연결한다.
67. Signal Dispute & Correction Workflow
사용자는 신호 상세에서 데이터 오류, 설명 오류, 중복, 무효화 지연, 성과 계산 오류를 신고할 수 있다.
신고에는 signal_id와 관련 lineage가 자동 첨부되며 사용자가 원시 로그를 직접 수집할 필요가 없게 한다.
검토 결과는 CONFIRMED_ERROR, EXPECTED_BEHAVIOR, DATA_PROVIDER_ISSUE, NEEDS_MORE_DATA로 분류한다.
오류가 확인되면 영향 범위, 수정 시각, 재계산 여부와 고객 영향 조치를 기록한다.
수정된 신호는 원본 이력을 삭제하지 않고 정정 표시와 변경 내용을 제공한다.
68. Explain Quality Standard
Explain 템플릿 변경은 대표 신호 fixture와 금지 표현 검사를 통과해야 한다.
AI가 설명 문장을 생성하더라도 계산 사실과 위험 문구는 구조화 데이터에서 강제한다.
69. Responsible UX & Behavioral Safety
과도한 거래를 유도하는 연속 알림, 손익 축하 애니메이션, 긴급성을 과장하는 카운트다운을 사용하지 않는다.
손실 후 거래 확대, 과도한 포지션 집중, 반복적인 위험 경고 무시가 감지되면 휴식·한도 점검을 제안한다.
랭킹은 단기 수익률만으로 정렬하지 않고 위험, 표본, MDD, 데이터 품질을 함께 노출한다.
다크 패턴을 금지하고 구독 해지와 알림 해제를 가입·활성화보다 부당하게 어렵게 만들지 않는다.
70. Transparency & Status Communication
상태 페이지에 API, 시장 데이터, Scanner, 알림, Paper Trading의 현재 상태와 과거 장애를 제공한다.
중대한 데이터 오류는 단순 장애가 아니라 영향을 받은 시장·기간·신호 유형을 설명한다.
분기별 투명성 보고서에 신호 수, 정정률, 데이터 품질, 알림 실패, 보안·개인정보 요청 통계를 집계한다.
성과 통계는 유리한 기간만 선택하지 않고 표본·기간·비용 조건을 함께 공개한다.
71. User Data Rights & Account Lifecycle
사용자는 프로필, 관심종목, 전략, 알림, Paper 기록, 피드백 데이터를 기계 판독 가능한 형식으로 내보낼 수 있다.
탈퇴는 즉시 로그인 차단 후 법적 보존 대상과 삭제 대상을 분리하고 완료 상태를 안내한다.
휴면·탈퇴·구독 만료·재가입 상태별 데이터 보존과 복구 가능 범위를 정의한다.
마케팅 동의와 필수 서비스 알림 동의를 분리하고 변경 이력을 보존한다.
72. v1.1 Data Model, API & Service Metrics
API 추가: /api/support/cases, /api/signals/{id}/disputes, /api/me/data-export, /api/me/account-deletion, /api/status.
73. Public Integration Boundary
외부 공개 범위는 읽기 전용 시세·신호·사용자 승인 Webhook부터 시작하고 주문·관리자 API는 공개하지 않는다.
OAuth 2.1 Authorization Code + PKCE를 사용하고 scope를 watchlist:read, signals:read, alerts:write처럼 최소화한다.
개인 API Token은 만료, 이름, 마지막 사용, IP 제한, 즉시 폐기를 지원하며 원문을 다시 표시하지 않는다.
파트너별 quota, 데이터 재배포 범위, 캐싱 가능 기간을 계약과 기술 정책으로 동시에 강제한다.
74. Webhook Delivery Contract
Webhook은 event_id, type, schema_version, occurred_at, data를 포함하고 HMAC 서명을 제공한다.
재시도는 지수 백오프와 최대 기간을 가지며 수신자는 event_id로 멱등 처리한다.
Endpoint 검증, 비밀키 회전, 일시 중지, 최근 전달 로그와 수동 재전송을 제공한다.
민감 정보와 사용자가 승인하지 않은 관심종목·성과 데이터는 payload에 포함하지 않는다.
75. Strategy SDK & Sandbox
전략 확장은 제한된 지표 입력과 구조화된 SignalCandidate 출력 계약을 사용하는 SDK로 정의한다.
사용자 코드는 네트워크, 파일시스템, 비밀값, 운영 DB에 직접 접근할 수 없는 격리 환경에서 실행한다.
CPU, 메모리, 실행시간, 결과 수, 로그 크기 제한과 강제 종료를 적용한다.
전략은 deterministic mode, 고정 데이터 fixture, 비용·미래 데이터 참조 검사를 통과해야 한다.
초기에는 내부·승인 파트너 전략만 허용하고 임의 사용자 코드 업로드는 후순위로 둔다.
76. Marketplace Review & Ranking
Marketplace 순위는 판매량이나 단기 수익률만 사용하지 않고 위험, 표본, 안정성, 신고율, 최신성을 포함한다.
제작자는 불리한 성과 구간을 삭제할 수 없고 새 버전은 기존 리뷰·성과와 분리한다.
77. Creator Economics & Disputes
유료 전략은 가격, 플랫폼 수수료, 세금 처리, 정산 주기, 환불 조건을 명시한다.
정산은 구매·환불·차지백 원장을 기반으로 하며 제작자 잔액과 회계 합계를 대사한다.
표절, 허위 성과, 저작권, 상표, 악성 코드 신고와 임시 비공개 절차를 둔다.
투자 손실 자체는 환불 사유로 약속하지 않으며 기능 미제공·허위 표시와 구분한다.
78. Partner & Developer Operations
Developer Portal에 API 문서, SDK, 변경 이력, 상태, 샌드박스, 사용량과 오류 로그를 제공한다.
API 변경은 deprecation 공지, 사용량 기반 영향 대상 통지, sunset 기간을 거친다.
파트너 앱은 이름, 도메인, 개인정보처리방침, 요청 scope, Webhook endpoint 검증을 거쳐 승인한다.
파트너 장애나 오용이 베인 핵심 서비스에 전파되지 않도록 별도 quota와 circuit breaker를 적용한다.
79. v1.2 Data Model, API & Ecosystem Gates
API 추가: /oauth/authorize, /oauth/token, /api/v1/webhooks, /api/v1/developer/usage, /api/v1/strategies/packages, /api/v1/marketplace.
생태계 출시 게이트: scope 검증, Webhook 서명·재시도, 샌드박스 탈출 테스트, 전략 재현성, 정산 대사, 데이터 라이선스 확인.
실거래 주문 권한, 무제한 사용자 코드, 원시 데이터 재판매는 v1.2 범위에서 제외한다.
80. 결론
v1.2의 핵심은 베인의 신뢰·보안 경계를 유지하면서 외부 앱과 전략 제작자가 안전하게 기능을 확장할 수 있게 만드는 것이다. 공개 API, Webhook, Strategy SDK와 Marketplace는 최소 권한, 격리 실행, 검증 가능한 성과와 정산 원장을 전제로 제공한다. 생태계 확장은 핵심 제품의 데이터 권리, 성능, 사용자 안전을 침해하지 않는 범위에서 단계적으로 승인한다.
