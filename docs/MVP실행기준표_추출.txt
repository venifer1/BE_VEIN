베인(VEIN) 내부 알파 · 상용 MVP 실행 기준표
4주 내부 알파 범위·DB·화면·API 상세 · v1.2 · 보강 통합 · 2026-06-13
문서 효력
이 문서는 기존 베인 개발 기획서 v1.2의 내부 알파 및 첫 상용 MVP 범위를 구체화한다. 범위가 충돌할 경우 본 문서의 포함/제외 결정과 완료 기준을 우선 적용한다.
1. 범위 결정
첫 수직 기능
• 코인 캔들 수집 → ABC 탐지 → 신호 저장 → 모바일 신호 목록 → 신호 상세·차트 표시
• 이 흐름이 골든 데이터, API, DB, 모바일 화면, 실패 처리까지 통과하기 전에는 결제·Paper Trading·외부 생태계 기능을 시작하지 않는다.
내부 알파 완료 정의
• 대표 코인 20개에서 1시간·4시간·일봉 캔들을 안정적으로 수집하고 데이터 최신성·결측 상태를 표시한다.
• ABC·삼각수렴 결과가 Python 골든 fixture와 합의된 허용 오차 내에서 동일하다.
• 신호 목록/상세, 관심종목, 알림 생성·해제의 정상·빈 화면·실패 화면이 모바일에서 동작한다.
2. 4주 내부 알파 실행 계획
주차별 비기능 기준
중단 기준: 2주차 종료 시 ABC 골든 테스트가 안정화되지 않으면 삼각수렴·알림을 미루고 캔들 계약과 ABC 동일성 확보에 집중한다.
3. 요구사항 추적표
각 행의 완료 조건, API, DB, 테스트, 실패·빈 화면 처리가 모두 연결되어야 구현 완료로 판정한다.
4. Python → Spring Boot/Next.js 이관표
골든 fixture 필수 메타데이터
• fixture_id, provider, symbol, timeframe, candle 범위, timezone, Python commit, 알고리즘 파라미터, 기대 피벗·상태·가격, 허용 오차를 JSON에 고정한다.
• Java 결과 불일치 시 기존 Python을 무조건 정답으로 두지 않는다. 데이터 정규화 차이, 버그 수정 여부를 기록하고 fixture 버전을 올린다.
5. 완료 판정·출시 게이트·충돌 해소
범위 충돌 해소 결정
내부 알파 Go/No-Go
첫 상용 MVP 진입 조건
• 내부 알파 종료 후 2주 이상 탐지 정확도, 중복 알림률, 데이터 누락률, 모바일 오류율을 측정하고 목표값을 확정한다.
• 측정값 없이 기능을 추가하지 않는다. 범위 변경은 새 기능 추가보다 기존 P0 완료에 미치는 일정·품질 영향을 먼저 기록한다.
현재 개발 우선순위: DATA-01 → ABC-01 → SIGNAL-01 → MARKET-01 → TRI-01 → WATCH-01 → ALERT-01 → AUTH/OPS 안정화.
6. 내부 알파 DB 논리 모델
설계 원칙
• PostgreSQL 기준이다. 가격·수량은 float가 아닌 NUMERIC을 사용하고, 모든 업무 시간은 TIMESTAMPTZ/UTC로 저장한다.
• 공급사 심볼과 내부 instrument_id를 분리한다. 캔들·신호의 재현에 필요한 provider, timeframe, algorithm_version, parameter_version을 보존한다.
• 내부 알파에서는 범용 JSON 남용을 피한다. 가변 근거와 원본 응답 참조만 JSONB로 두고 조회·무결성 필드는 정규 컬럼으로 둔다.
핵심 관계
• instruments 1─N provider_symbols / candles / pattern_signals / watchlist_items / alerts
• pattern_signals 1─N signal_evidence, pattern_signals 1─N notifications
• users 1─N refresh_tokens / watchlists / alerts / notifications, watchlists 1─N watchlist_items
삭제 원칙: 캔들·신호는 운영 재현을 위해 즉시 물리 삭제하지 않는다. 사용자 탈퇴 시 사용자 소유 데이터는 정책에 따라 삭제·익명화하되 시장 데이터는 유지한다.
7. 모바일 화면 구성과 상태 설계
내부 알파 IA
하단 탭은 신호 · 관심 · 알림 · 설정 4개로 제한한다. 종목 상세와 신호 상세는 목록에서 진입하는 스택 화면으로 둔다.
핵심 화면 흐름
• 로그인 → 통합 신호함 → 신호 상세 → 차트 근거 확인 → 관심종목 등록 → 패턴 알림 생성 → 알림함 → 동일 신호 상세 복귀
• 통합 신호함 → 필터 결과 0건 → 필터 초기화 또는 관심종목 해제 안내
• 신호 상세 → 캔들 일부 누락 → 마지막 정상 데이터·누락 구간 표시 → 재시도
화면별 공통 규칙
8. 내부 알파 API 계약
공통 규칙
• Base path는 /api/v1, JSON은 snake_case, 시간은 ISO-8601 UTC, 가격·수량은 문자열 Decimal로 직렬화한다.
• 성공 응답은 data와 meta를 사용한다. 오류는 code, message, trace_id, field_errors를 포함한다.
• 목록은 cursor 기반으로 최신순 정렬을 고정하고 page_size 기본 20, 최대 100으로 제한한다.
대표 신호 상세 응답
{ "data": { "id": "sig_123", "type": "ABC", "status": "NEAR_COMPLETION", "instrument": { "id": "ins_btc", "symbol": "KRW-BTC" }, "timeframe": "4h", "detected_at": "2026-06-12T15:00:00Z", "score": "82.5", "evidence": [{ "type": "PIVOT_A", "candle_time": "...", "price": "142000000" }], "invalidation": { "rule": "A_LOW_BREAK", "price": "..." }, "algorithm_version": "abc-java-1.0.0" }, "meta": { "trace_id": "...", "freshness": "FRESH" } }
API 완료 조건: OpenAPI 문서, Controller 계약 테스트, DB 통합 테스트, 권한 테스트, 화면 mock과 실제 API 간 schema diff가 모두 통과해야 한다.

구현 순서와 마이그레이션
이번 범위에서 생성하지 않는 것

10. v1.2 보강 통합 (확정)
아래 항목은 기존 본문을 갱신·보완하는 확정 사항이다. 본문 표/섹션과 충돌하면 본 절을 우선한다.
10.1 착수 전 필수 (P0) — 본문 수정
• 확정봉 처리: §6 candles에 is_final(BOOLEAN) 컬럼을 추가한다(또는 open_time+timeframe로 마감 시각 산출). 패턴 탐지는 확정봉만 사용하고, 미확정봉은 차트 표시 전용으로 한다. (기획서 §30 provisional 원칙 반영)
• signal_key 정의: §6 pattern_signals.signal_key = algorithm_version + rule_id + instrument_id + timeframe + anchor_candle_time. (멱등 저장·중복 방지)
• 골든 허용오차 수치화: §4 fixture 메타에 고정 — 피벗 index 완전 일치 / 가격 상대오차 ≤ 0.05% / 점수 ±1.0점 / 추세선 기울기 상대오차 ≤ 1%. 2주차 Go/No-Go 판정에 이 값을 사용한다.
• lookback·초기 백필: §2 1주차에 명시 — 주기(timeframe)별 초기 히스토리 최근 1,000봉 적재, ABC/삼각수렴 최소 lookback 봉 수를 파라미터로 고정.
10.2 결정 사항 (P1) — 해당 주차 착수 직전 확정
10.3 정합성 정정
• delivery_attempts 테이블을 §6에 추가: id, notification_id(FK), channel, status, attempt_no, error_code, attempted_at. (요구사항 추적표 ALERT-01과 일치)

부록 B. Flyway DDL (V1~V4)
가격·수량은 NUMERIC, 시간은 TIMESTAMPTZ(UTC). 본문 §6 논리모델 + §10 보강(is_final, signal_key, delivery_attempts) 반영. id는 BIGINT GENERATED ALWAYS AS IDENTITY.
V1__market.sql — 수집 기반 (1주차)
CREATE TABLE instruments (
  id             BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  market         VARCHAR(16)  NOT NULL,           -- CRYPTO
  exchange       VARCHAR(16)  NOT NULL,           -- UPBIT
  symbol         VARCHAR(32)  NOT NULL,           -- KRW-BTC
  name           VARCHAR(64),
  quote_currency VARCHAR(8)   NOT NULL,           -- KRW
  status         VARCHAR(16)  NOT NULL DEFAULT 'ACTIVE',
  UNIQUE (exchange, symbol)
);
CREATE INDEX ix_instruments_market_status ON instruments(market, status);
 
CREATE TABLE provider_symbols (
  id              BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  instrument_id   BIGINT NOT NULL REFERENCES instruments(id),
  provider        VARCHAR(16) NOT NULL,
  provider_symbol VARCHAR(32) NOT NULL,
  UNIQUE (provider, provider_symbol)
);
 
CREATE TABLE candles (
  instrument_id BIGINT        NOT NULL REFERENCES instruments(id),
  timeframe     VARCHAR(4)    NOT NULL CHECK (timeframe IN ('1h','4h','1d')),
  open_time     TIMESTAMPTZ   NOT NULL,           -- 업비트 candle_date_time_utc
  open          NUMERIC(24,8) NOT NULL,
  high          NUMERIC(24,8) NOT NULL,
  low           NUMERIC(24,8) NOT NULL,
  close         NUMERIC(24,8) NOT NULL,
  volume        NUMERIC(28,8) NOT NULL,
  provider      VARCHAR(16)   NOT NULL,
  is_final      BOOLEAN       NOT NULL DEFAULT TRUE,
  collected_at  TIMESTAMPTZ   NOT NULL DEFAULT now(),
  PRIMARY KEY (instrument_id, timeframe, open_time, provider)
);
CREATE INDEX ix_candles_open_time ON candles(instrument_id, timeframe, open_time DESC);
 
CREATE TABLE ingestion_runs (
  id             BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  provider       VARCHAR(16) NOT NULL,
  job_type       VARCHAR(24) NOT NULL,            -- BACKFILL | POLL | GAPFILL
  timeframe      VARCHAR(4),
  started_at     TIMESTAMPTZ NOT NULL,
  ended_at       TIMESTAMPTZ,
  status         VARCHAR(16) NOT NULL,            -- RUNNING|OK|FAILED
  fetched_count  INT DEFAULT 0,
  inserted_count INT DEFAULT 0,
  gap_count      INT DEFAULT 0,
  error_code     VARCHAR(48)
);
CREATE INDEX ix_ingestion_provider_started ON ingestion_runs(provider, started_at DESC);
V2__signal.sql — 패턴 신호 (2주차)
CREATE TABLE pattern_signals (
  id            BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  instrument_id BIGINT NOT NULL REFERENCES instruments(id),
  type          VARCHAR(16) NOT NULL,             -- ABC | TRIANGLE
  timeframe     VARCHAR(4)  NOT NULL,
  status        VARCHAR(20) NOT NULL,             -- DETECTED|NEAR_COMPLETION|INVALIDATED|EXPIRED|CLOSED
  score         NUMERIC(6,2),                     -- 알파: 완성도 기본값(또는 NULL)
  detected_at        TIMESTAMPTZ NOT NULL,
  anchor_candle_time TIMESTAMPTZ NOT NULL,        -- ABC=B봉, TRIANGLE=마지막 꼭짓점 봉
  algorithm_version  VARCHAR(32) NOT NULL,        -- abc-java-1.0.0
  rule_id            VARCHAR(24) NOT NULL,        -- ABC / TRIANGLE
  invalidation_rule  VARCHAR(32),                 -- A_LOW_BREAK 등
  invalidation_price NUMERIC(24,8),
  expires_at    TIMESTAMPTZ,
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
  signal_key    VARCHAR(128) NOT NULL UNIQUE      -- algo|rule|instrument|timeframe|anchor
);
CREATE INDEX ix_signals_type_status_det ON pattern_signals(type, status, detected_at DESC);
 
CREATE TABLE signal_evidence (
  id            BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  signal_id     BIGINT NOT NULL REFERENCES pattern_signals(id) ON DELETE CASCADE,
  evidence_type VARCHAR(24) NOT NULL,             -- PIVOT_0|PIVOT_A|PIVOT_B|TREND_UPPER|TREND_LOWER|C_TARGET
  sequence_no   INT NOT NULL,
  price         NUMERIC(24,8),
  candle_time   TIMESTAMPTZ,
  payload       JSONB,
  UNIQUE (signal_id, evidence_type, sequence_no)
);
V3__user.sql — 인증·관심 (3주차)
CREATE TABLE users (
  id            BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email         VARCHAR(254) NOT NULL,
  password_hash VARCHAR(100) NOT NULL,            -- BCrypt
  role          VARCHAR(16)  NOT NULL DEFAULT 'TESTER',
  status        VARCHAR(16)  NOT NULL DEFAULT 'PENDING',  -- PENDING|APPROVED|LOCKED
  created_at    TIMESTAMPTZ  NOT NULL DEFAULT now()
);
CREATE UNIQUE INDEX ux_users_email ON users(lower(email));

E-2. ABC 파라미터·규칙 (config 실측값)
ABC 규칙 요약:
1) 0(고점): 직전 win평균 대비 (1+0.10)배 이상 돌출만 채택
2) A(저점, A>0): 낙폭 drop_pct = (0-A)/|0| >= 0.20, STRICT_WAVE면 0~A 사이 0 미돌파
3) B(고점, B>A): retrace = (B-A)/(0-A) in [0.236, 0.886], B<0 유지, A~B 사이 A 미이탈
4) C 목표가 c_100 = B - (0-A)
5) 정렬: 최근(piB index) 우선, 0값 기준 dedup, 상위 3개
evidence: PIVOT_0/PIVOT_A/PIVOT_B(가격·봉시각), C_TARGET(c_100)
invalidation: A_LOW_BREAK (저가가 A 이탈 시 INVALIDATED)
E-3. 삼각수렴 파라미터·규칙 (detector 실측값)
삼각 규칙 요약:
- 상단 피벗 3개(h0<h1<h2) + 하단 피벗 3개(l0<l1<l2), 교차 순서 h0<l0<h1<l1<h2<l2
- 단조성: 상단 비상승, 하단 비하락 (mono_tol 0.004)
- 유형(_triangle_type):
    upper_drop=(h0-h2)/|h0|, lower_rise=(l2-l0)/|l0|
    symmetric : upper_drop>=0.006 and lower_rise>=0.006
    ascending : upper_drop<=0.008 and lower_rise>=0.006
    descending: upper_drop>=0.006 and lower_rise<=0.008
- 현재폭/초기폭 width_ratio <= 0.75, 현재가가 채널 내부(±tolerance)
- target = (upper_now+lower_now)/2, 정렬: width_ratio 오름차순
evidence: TREND_UPPER(h0,h1,h2), TREND_LOWER(l0,l1,l2), 각 좌표 payload

H-2. JwtService (발급·검증)
@Service
public class JwtService {
  private final SecretKey key;
  private final long accessTtl, refreshTtl;
  public JwtService(@Value("${JWT_SECRET}") String secret,
                    @Value("${JWT_ACCESS_TTL}") long accessTtl,
                    @Value("${JWT_REFRESH_TTL}") long refreshTtl) {
    this.key = Keys.hmacShaKeyFor(secret.getBytes(StandardCharsets.UTF_8));
    this.accessTtl = accessTtl; this.refreshTtl = refreshTtl;
  }
  public String issueAccess(User u, Instant now) {
    return Jwts.builder().subject(u.getId().toString())
        .claim("role", u.getRole())
        .issuedAt(Date.from(now))
        .expiration(Date.from(now.plusSeconds(accessTtl)))
        .signWith(key).compact();
  }
  public Jws<Claims> parse(String token) {      // 만료/위조 시 JwtException
    return Jwts.parser().verifyWith(key).build().parseSignedClaims(token);
  }
}
H-3. JwtAuthFilter
public class JwtAuthFilter extends OncePerRequestFilter {
  private final JwtService jwt;
  protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res,
                                  FilterChain chain) throws ... {
    String h = req.getHeader("Authorization");
    if (h != null && h.startsWith("Bearer ")) {
      try {
        Claims c = jwt.parse(h.substring(7)).getPayload();
        var auth = new UsernamePasswordAuthenticationToken(
            c.getSubject(), null,
            List.of(new SimpleGrantedAuthority("ROLE_" + c.get("role"))));
        SecurityContextHolder.getContext().setAuthentication(auth);
      } catch (JwtException ignore) { /* 인증 미설정 → 401 */ }
    }
    chain.doFilter(req, res);
  }
}
H-4. AuthService — login / refresh / logout
public AuthResult login(String email, String rawPw, Instant now) {
  User u = users.findByEmailIgnoreCase(email)
      .orElseThrow(() -> new ApiException("AUTH_INVALID"));
  if (!encoder.matches(rawPw, u.getPasswordHash())) throw new ApiException("AUTH_INVALID");
  if (u.getStatus() == LOCKED)        throw new ApiException("USER_LOCKED");
  if (u.getStatus() != APPROVED)      throw new ApiException("USER_NOT_APPROVED");
  String access  = jwt.issueAccess(u, now);
  String refresh = issueRefresh(u, now);     // 랜덤 토큰 → hash 저장(refresh_tokens)
  return new AuthResult(access, refresh, u);
}
 
public AuthResult refresh(String refreshToken, Instant now) {
  RefreshToken rt = tokens.findByTokenHash(sha256(refreshToken))
      .filter(t -> t.getRevokedAt() == null && t.getExpiresAt().isAfter(now))
      .orElseThrow(() -> new ApiException("TOKEN_EXPIRED"));
  rt.revoke(now);                            // 회전: 기존 폐기 후 신규 발급(재사용 탐지)
  User u = users.getById(rt.getUserId());
  return new AuthResult(jwt.issueAccess(u, now), issueRefresh(u, now), u);
}
 
public void logout(String refreshToken, Instant now) {
  tokens.findByTokenHash(sha256(refreshToken)).ifPresent(t -> t.revoke(now));
}
• refresh_token 원문은 저장하지 않고 SHA-256 해시만 저장한다(부록 B refresh_tokens.token_hash). 회전 시 재사용된 토큰이 들어오면 보안 이벤트로 기록.
